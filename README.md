# Swiggy Support Decision Intelligence (capstone)

All data is synthetic (produced by `generate_data.py`); nothing here reflects real Swiggy data. Every number below is copied from the files in `outputs/`, which are regenerated by the scripts. Shared code is in `common.py`.

## How to run

From a clean clone, with Python 3.10 or newer:

```
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python generate_data.py
python part1.py
python part2.py
python part3.py
python part4.py
```

On Linux or macOS activate with `source .venv/bin/activate`. `generate_data.py` must print `800 10 170 7cb48ef89914049d76954530b6482e04`. The data file is byte-sensitive (`.gitattributes` disables line-ending conversion for it). Optional self-check: `python -m unittest discover tests`.

## Part 1 findings

**R1.1** H0 (mean resolution time = 8.0 minutes) is rejected: `z_stat` = 2.8930, which is above the critical value 1.96 (`reject_h0` = yes). A Type I error here would be concluding that the true average resolution time differs from 8 minutes when the staffing assumption is in fact right. The sample mean is 8.9382 minutes, a gap of 0.9382 minutes (about 56 seconds, 11.7 percent above plan); the 95% interval is 8.3026 to 9.5738. The gap is statistically clear, but whether it matters depends on volume: across many thousands of tickets a minute each adds up to real staffing hours, while for a single ticket it is small.

**R1.2** `n_required` = 1293 tickets for a margin of 0.5 minutes, against 800 rows available. The present sample gives a margin of about 0.64 minutes (1.96 x 0.3243), so the team needs roughly 500 more tickets to reach half a minute.

**R1.3** `gd_slope_gap` = 0.0000. The squared-error cost is a convex bowl with one minimum, and with standardised X4 and 500 updates at rate 0.1 the descent settles at the bottom, which is exactly where the closed form lands (`gd_J100` and `gd_J500` are both 40.3698).

**R1.4** `resid_sd_ratio_raw` = 3.7525 and `resid_sd_ratio_log` = 1.0396. The raw model shows a strong funnel (residual spread in the upper half of fitted values is 3.75 times that of the lower half); the log-log model removes it (ratio close to 1).

**R1.5** Predictors with absolute coefficient above 0.05 in the Task 1.7 model: ln(X4) (1.1576), X2 earlier tickets (0.0940), X3 SLA consumed (0.1067) and X6 reopened flag (0.1518). This is a mechanical rule on unlike units, not a ranking of importance. `mr_adj_r2` = 0.7403 against `loglog_adj_r2` = 0.6561, so the extra predictors earn their place (adjusted R-squared rises by about 0.08 even after the penalty for seven predictors).

## Part 2 findings

**R2.1** Lowest to highest after 200 updates: eta 1.0 (0.3703), eta 0.1 (0.3776), eta 0.01 (0.5091). A rate that is too small barely moves in 200 steps and is still far from the minimum, while the large rate was still stable here and converged fastest.

**R2.2** The three largest absolute weights are X3 SLA consumed ratio (0.9013), X1 tenure (-0.5554) and X2 earlier tickets (0.5505). The largest odds ratio is 2.4629 for X3: when a ticket reaches an agent with one training SD more of its resolution-time target already used, the odds of escalation are multiplied by about 2.5.

**R2.3** `blind_accuracy` = 0.7875 against 0.8042 at tau 0.5: a model that never flags anything scores almost as high, so accuracy hides the failure to catch escalations (only 24 of 51 caught at tau 0.5). Lowering tau from 0.5 to 0.3 raised recall from 0.4706 to 0.7451 and cut precision from 0.5455 to 0.4634.

**R2.4** At tau 0.3 the logistic model has `f1` 0.5714 and recall 0.7451; KNN (K = 5) has `knn_f1` 0.3696 and `knn_recall` 0.3333. Logistic regression is clearly better on both.

**R2.5** Deploy the logistic model at the cost-chosen threshold `cost_tau` = 0.1500. On test rows it costs INR 6050 (`cost_test_at_tau`), against INR 11800 at tau 0.5 and INR 20400 for flagging nobody. The threshold was chosen on training rows so that the test rows stay an honest, untouched estimate of future cost.

## Part 3 findings

**R3.1** WCSS drops: WCSS(2) - WCSS(3) = 659.8282, WCSS(3) - WCSS(4) = 108.0739, WCSS(4) - WCSS(5) = 171.0575, WCSS(5) - WCSS(6) = 45.5466. The rule gives `elbow_k` = 3, because the 3-to-4 drop is less than half of the 2-to-3 drop. The drops do not shrink steadily (the 4-to-5 drop is larger than the 3-to-4 drop): the pinned starting rows give a reproducible solution, not necessarily the global optimum.

**R3.2** Segment profiles (`part3_segments.csv`):
- Segment A, "Fast-track regulars" (322 tickets): little SLA used (0.2250), long tenure, few repeat contacts, quick resolution (mean 3.5976 minutes), outcome rate 0.0186. Action: auto-resolve and keep out of supervisor review.
- Segment B, "Repeat-contact, high-spend, slow" (255 tickets): 6.0706 earlier tickets, highest spend, slowest resolution (17.1248 minutes), outcome rate 0.2353. Action: route to experienced agents and give them extra handling time in staffing plans.
- Segment C, "Late-arriving tickets" (223 tickets): SLA already 0.7118 consumed, short tenure, outcome rate 0.4664. This is the highest outcome rate, so tickets in C should be flagged for supervisor review first and prioritised in the queue.

**R3.3** Single linkage cuts into 4 clusters: E1; E2+E3+E6; E4; E5. Complete linkage cuts into 2 clusters: E1+E4+E5 and E2+E3+E6. Single linkage joins clusters through their closest pair, so it chains and its last merge height (3.4000) is not far above earlier ones; its largest gap comes early, leaving four groups. Complete linkage uses the farthest pair, so the final merge jumps to 7.9000, giving a clear two-group cut.

**R3.4** The mean vector of the standardised data is all zeros. PC1 is a contrast: positive loadings for X1 tenure (0.5317) and X5 satisfaction (0.4418), negative for X3 SLA consumed (-0.5187), X2 earlier tickets (-0.4100) and X4 account value (-0.2916). Three components are needed for at least 80% of variance (`components_for_80pct` = 3; the first two keep 0.7593). `mean_pc1_segment_A/B/C` are 1.7773, -0.7831 and -1.6709, so PC1 orders the segments from established, calm customers (A) to late, low-satisfaction tickets (C).

## Part 4 findings

**R4.1** S4 (tenure at most 24 months) is the best split by both information gain (0.1252) and Gini gain (0.0606) because it separates the training rows into a high-escalation side (86 of 188) and a low-escalation side (33 of 372) better than the other candidates. A tree grown until every leaf is pure memorises noise in the 560 training rows, so it fits the training set perfectly but predicts new tickets worse. A maximum depth, or a minimum number of records per leaf, stops a tree from growing too deep.

**R4.2** I would ship the logistic model: `f1` 0.5714 and recall 0.7451 at tau 0.3, against stump 0.5532 and 0.7647, hard vote 0.5344 and 0.6863, soft vote 0.5507 and 0.7451, KNN 0.3696 and 0.3333. Combining models did not help: neither vote beat the logistic model on f1.

**R4.3** After round 1 normalisation the two misclassified points (3 and 7) carry a total weight of 0.5000. Round 2 trusts h2 more because its weighted error (0.1667) is smaller than the 0.2500 of h1, which gives a larger alpha (0.8047 against 0.5493).

Model B: W_xh is 128 x 64, W_hh is 128 x 128 and W_hy is 16 x 128, so `rnn_total` = 26768. It does not grow with sequence length because the same weights are reused at every step.

For 10 classes I would use ReLU in hidden layers and softmax at the output with categorical cross-entropy loss.

In a very deep plain network the gradient is multiplied by many small factors on its way back, so it shrinks to almost nothing and the early layers stop learning. A skip connection adds the input to a block's output, giving the gradient a direct path back to early layers.

## Model-choice memo

To: Head of Customer-Support Operations

Recommendation: put the logistic-regression model into production, flagging a ticket for supervisor review when its escalation probability is at least 0.15. A review costs about INR 50 and a missed escalation about INR 400, and 0.15 is the threshold with the lowest cost on training tickets (INR 12150).

On 240 held-out tickets this rule costs INR 6050. Flagging at 0.5 costs INR 11800, and flagging nobody costs INR 20400, so the rule roughly halves cost against the default threshold and cuts it by about 70 percent against doing nothing. At the milder 0.3 threshold the model catches 74.51 percent of escalations (F1 0.5714). K-nearest neighbours reached only F1 0.3696 and a one-question tenure rule 0.5532; majority and averaged votes of the three did not beat logistic regression, so the extra complexity is not justified. The cost of the other models at 0.15 was not computed.

Main driver: the share of the resolution-time target already used when the ticket reaches an agent. Raising it by one standard deviation multiplies escalation odds by about 2.5.

Risk: the evidence is one split with only 51 escalated test tickets, on synthetic data, so the cost and the threshold are noisy and should be re-checked on live tickets after a pilot.

Of the two network ideas, Model B (ticket text, 26768 parameters) is the one worth building first, and only once the structured model is in production; Model A (order photos) can wait.

## Limitations

1. The data is synthetic and generated from known formulas, so the findings say nothing about real Swiggy tickets and real data would be messier.
2. One fixed 560/240 split is used: the best K, the threshold and all test costs are valid for that split only and could change on another split.
3. The test set has only 51 escalated tickets, so recall, precision and the INR costs have wide uncertainty (a few tickets change the cost by hundreds of rupees).
4. The costs of INR 50 and INR 400 are rough planning figures; the best threshold moves if they change.
5. K-means uses pinned starting rows and may not reach the global optimum; the z-test assumes independent tickets, and tickets from the same customer or day may not be.
